# 雨玻璃格边接缝（每颗水珠自己的边界）

跟立方体面边接缝（`RainGlass-Seams.md`）**不是同一件事**。这条在面正中间也有，
表现为「很多水珠有自己的独立边界」+「下落时冒出临时接缝」。

格边位于 `uvx = k/12`（`grid.x = 12`）。探针 `probe_align_seam.py` 第 6 节直接量跨界跳变。

## 量到的跳变

| 配置 | 均值 | p95 | 最大 | 跳>0.05 的比例 |
|:---|:---|:---|:---|:---|
| 三盘 + 合体（最初） | 0.0498 | **0.3528** | 2.0942 | **11.1%** |
| 三盘，关合体 | 0.0201 | 0.1435 | 0.8747 | 8.2% |
| 单盘，关合体（≡ blog） | 0.0108 | 0.0586 | 0.8747 | 5.3% |
| **三盘 + 邻列自己的 colShift（现状）** | **0.0028** | **0.0009** | 0.3003 | **1.9%** |

p95 0.35 是掩膜量程的三分之一，就是一条看得见的硬线。blog 自己也有 5.3%——那是
Heartfelt 原生的格边裁切，合体本来就是为了修它，结果把它放大了 6 倍。

**修完机制 B 后 p95 是 0.0009，比 blog 还好 65 倍。** 三盘方案这才真正起到"不裁水珠"的作用。
残余的 max 0.3003 来自珠串：`y2 = frac(UV.y*10) + (st.y-0.5)` 里的 `st.y` 仍是本列行框，
跨列会跳。占比 1.9%，且 blog 同构，先留着。

对 blog 对齐**零代价**：rms 0.0763 → 0.0761。

## 三条机制，量过的

**A. x 位置——不是它。** 我先猜的是这条，被数据否掉。三格质心恰好能望远镜掉：

```
xCom_i - 1  ==  lerp(x_i-1, xCom_{i+1}, w)  ==  (x_i - 1 + x_j·w)/(1+w)
```

对任意 `w` 恒等。符号推导和数值都验过。别再往这条上查。

**B. 邻格盘画的是幽灵水珠。** `colShift = N(id.x)` 是逐列的，`id.y` 又是从它推出来的，
而代码里左右邻居是 `DropPos(id.x±1, id.y)`——**用的是本列的 `id.y`**。
左边那列自己画的中心珠是 `DropPos(id.x-1, id.y')`，`id.y'` 来自 `N(id.x-1)`。

实测两者行号**在 38.6% 的采样上不一致**。也就是说三盘方案里那两片"邻居"，
有近四成根本不是邻列真实存在的水珠，是凭空多出来的一颗，自带边界。
这解释了"关合体"那一行为什么还是比 blog 差 2.4 倍（p95 0.144 vs 0.059）。

**C. 合体的 y 是观察者相关的。** 本格把中心珠往 `yCom_i` 拉，权重 `max(w_l, w_r)`；
右边那格把**同一颗**珠当左邻居，往 `yCom_{i+1}` 拉，权重只有 `w_r(i)`。
而 `yCom` 还是按质量加权的三格质心，两边的三格窗口不同。实测落差：

| `w_l(i)` | `w_r(i)` | 本格给的 y | 右格给的 y | 落差 |
|:---|:---|:---|:---|:---|
| 0.00 | 0.50 | 0.58500 | 0.62609 | 0.041 |
| 0.50 | 0.50 | 0.55000 | 0.62609 | 0.076 |
| 1.00 | 0.50 | 0.50000 | 0.62609 | 0.126 |

水珠在 st.y 上的半高只有 `R/6 = 0.067`。落差 0.041~0.126 是**半高的 0.6~1.9 倍**，
两侧把同一颗珠放在了完全不同的高度。`w` 随下落连续变化 → 接缝时隐时现。
这就是"莫名其妙的临时接缝"。

## 为什么不能「让接缝位置不刷水珠」

距离度量是 `|(st-p)·(1,6)|`，`a.yx` 只压 st.y，**st.x 方向盘的半宽就是整个 R=0.4**，
占 1.0 宽格子的 **80%**。珠心本来就散布在 ±0.35。
要两边都不碰格边得 `|x| ≤ 0.10`，只剩珠心可用范围的 29%。

所以格边不是一条可以让开的细缝，它**从大多数水珠身上穿过去**。挖空它等于把水珠削掉一大块，
或者挤出每 1/12 UV 一条的规则竖向干带（线上机位一个面约 8 条）。这条路不通。

## 现状

**机制 B 已修。** `MF_WS_DropLayer2` 里左右邻居现在走邻列自己的行框：

```
uv_y2L = uv_yt + N(id.x-1)      # 邻列自己的 colShift
id2yL  = floor(uv_y2L * grid.y) # 邻列自己的行号
st_yL  = frac(uv_y2L * grid.y)  # 邻列自己的格内 y
pos_l  = DropPos(id.x-1, id2yL)
左盘距离 = |(st.x - (pos_l.X - 1), st_yL - pos_l.Y) * a.yx|
```

代价只有 2 次 `N` 哈希 + 2 组 Add/Mul/Floor/Frac，**`DropPos` 仍是 3 次**。

**机制 C 未修，`合体强度` 默认 0**（两个 MI 和两张父材质默认都是 0）。
不要在没治 C 之前把它调上去：现在邻列 y 在各自行框里，合体的 y 质心会跨框混算，
比修 B 之前更糟。合体的 x 权重只吃水平距（`dxl` 只取 `.R`），那部分不受影响。

## 机制 C 要怎么治（未做）

合体位移必须是**水珠自身的纯函数**，不能依赖观察格。观察格 `j` 要画水珠 `i` 的合体位置，
就得能算出 `i` 的完整邻域。三盘要画 `i-1, i, i+1`，每颗都要自己的左右邻居 →
需要 `i-2..i+2` 五列，`DropPos` 从 3 次涨到 5 次（每像素 54 → 90）。

更便宜的替代：**按奇偶固定配对**，每颗珠只属于一对，两个成员一起走向对心。
这样 `i` 的位置只依赖它的配对伙伴，三盘只需 `i-1..i+2` 四列（54 → 72）。
代价是只有奇偶对能合，会有固定的配对结构，可能看出规律。

最大那笔提速（三面降一面 ≈3×）够付上面任何一种账。
